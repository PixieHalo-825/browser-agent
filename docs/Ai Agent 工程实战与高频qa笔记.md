# AI Agent 工程实战与高频技术 QA 笔记

> 本文结合浏览器自动化智能体（基于 OpenManus + LangGraph + Playwright + MCP 架构）与本地 RAG 知识库实践，整理了 AI Agent 开发、评测、安全与落地中的 18 个高频工程问题与解决思路，适合技术复盘、面试准备与方案选型参考。

---

## 一、浏览器自动化智能体核心架构

### Q1. 面对动态网页、复杂弹窗和 Canvas 元素，如何提升浏览器 Agent 的定位稳定性？

传统 RPA 依赖固定 CSS/XPath 选择器，一旦遇到动态 class 名、iframe 嵌套、遮罩弹窗或 Canvas 渲染就会频繁失效。更稳妥的做法是设计**多模态四级降级流水线**（例如在 `locator.py` 中逐级兜底），由廉价到昂贵依次尝试：

1. **`dom-rule`（纯规则打分，零 LLM）**：基于属性、文本与结构特征直接匹配，速度最快、零 Token 成本。
2. **`dom-llm`（文本模型筛选）**：将精简后的 DOM 候选元素列表交由文本模型选择，成本低且可处理语义模糊的按钮。
3. **`vision-som`（Set-of-Mark 视觉选号）**：在页面截图上为可交互区域打编号标签，交由 VLM（如 Qwen-GUI-Plus）直接选择对应编号，抗动态 DOM 和复杂弹窗干扰。
4. **`vision-ground`（VLM 直接回归坐标）**：当元素完全不在 DOM 树中（如 Canvas 或纯图像按钮）时，由视觉模型直接回归 bbox 坐标进行点击。

同时，每次定位应记录**实际命中的通道与置信度**，既便于后续评测统计，也能快速发现规则层需要补强的薄弱点。

### Q2. 长链路浏览器任务如何编排？遇到报错或死循环如何实现“自我修复”？

长链路网页操作（如跨平台比价、竞品信息采集，通常超过 10 步）如果全部塞进单体 Chain 或单一 Prompt，模型很容易在多轮交互后遗忘目标或陷入重复点击。

建议基于 LangGraph `StateGraph` 构建分层状态机：**`Planner → (Executor ⇄ Tools) → Reviewer`**。

- **自我修复机制**：每步执行完毕后由 `Reviewer` 核对当前页面状态与工具返回结果，并做三向路由——`continue`（正常推进）、`replan`（携带失败原因回退给 `Planner` 重新规划替代路径）、`finish`（任务达成）。
- **四层防失控熔断**：
  1. `terminate` 异常短路（识别到不可恢复错误或安全风险时立即终止）；
  2. 单步 ReAct 内部思考轮数上限；
  3. 全局重规划（`replan`）次数上限；
  4. 全局总步数上限。

任何一层触发阈值均安全退出并保留完整执行日志，避免无限循环烧干 Token。

### Q3. 为什么 Agent 执行代码需要沙箱？如何兼顾安全性与本地可用性？

当 Agent 在数据分析、爬虫解析等场景下动态生成并执行 Python 脚本时，一旦模型出现幻觉或遭遇提示词注入，在宿主机直接运行极易引发误删文件、泄露环境变量或耗尽资源等风险。

工程上建议抽象统一的 `SandboxProvider` 接口，实现 **`auto` 模式三级自动探测降级**：

1. **优先 Daytona 云沙箱**：强隔离、独立环境，适合生产或高风险脚本。
2. **次选本地 Docker 容器**：当云沙箱不可用时自动切换，配置断网、只读文件系统、CPU/内存上限与执行超时。
3. **兜底 `local` 子进程**：仅在无容器环境的极简调试下启用，并强制输出明确的安全警告日志。

### Q4. 什么是 MCP？它和 Function Calling 有什么区别？

两者的定位在不同层级：

- **Function Calling（模型层能力）**：解决“大模型如何按约定 JSON 格式决定调用哪个函数与参数”，但每个应用仍需重复编写工具对接与维护代码。
- **MCP / Model Context Protocol（应用层通用协议）**：相当于 AI 生态的统一接口规范，解决“工具如何标准化接入与跨应用复用”。

在实践落地中，可将工具层拆分为独立的 MCP Server（例如**文件、搜索、浏览器**三个独立 Server），同时支持 **`stdio`**（本地进程通信）和 **`streamable-http`**（远程/容器服务通信）双传输模式，并通过 `docker-compose.yml` 一键容器化拉起。新增或下线工具时，只需在配置文件中增删 Server 名称即可热插拔，**Agent 核心代码零改动**。

## 二、Agent 选型、成本、性能与安全

### Q5. 什么时候用单 Agent，什么时候用多 Agent？

原则是**简单优先，避免过度设计**：

- **优先单 Agent**：任务边界清晰、步骤少（3~5 步内）、工具数量有限时，单 Agent 响应更快、Token 成本更低、调试链路更短。
- **采用多 Agent / 分层架构**：当任务链条长（>10 步）、需要明显不同的专长分工，或必须引入独立角色做质量验收与纠偏（如 `Planner / Executor / Reviewer` 分离）时，再拆分为多角色协作。

---

### Q6. 如何有效降低 Agent 的 Token 消耗（成本优化策略）？

1. **无 LLM 优先与模型分级路由**：能用确定性规则解决的绝不调模型（例如 `dom-rule` 零 Token 定位）；简单提取与分类用轻量模型，复杂规划再调用强模型，视觉 VLM 仅作兜底。
2. **输入瘦身**：向模型传递 DOM 前先做节点裁剪，只保留可交互元素；截图按需缩放压缩，避免每次都传无损大图。
3. **上下文压缩与步数熔断**：长链路任务定期对历史步骤做摘要，不把每一步的完整网页原文堆进历史对话；靠四层上限防止死循环烧费。
4. **高频结果缓存**：对重复查询与静态页面结构做本地缓存复用。

---

### Q7. 如何平衡 Agent 的响应速度与思考深度？响应慢怎么排查瓶颈？

- **速度与深度平衡**：按业务场景分层——实时交互型任务压缩思考步数并开启流式输出（Streaming）提升体感；后台异步任务（如竞品采集与报表生成）允许深度规划，同时向前端推送阶段性进度。
- **慢响应排查思路**：对全链路做**分段打点计时**，拆分出四块耗时占比：
  1. 网页加载与网络 I/O 耗时；
  2. 工具执行与沙箱启动耗时；
  3. 定位通道分布（如果大量请求掉进了高延迟的 `vision-som / vision-ground`，应优先反哺优化 `dom-rule` 规则）；
  4. 状态机中 `replan` 重规划次数是否异常偏高。

---

### Q8. 如何防止 Agent 的提示词注入（Prompt Injection）？

浏览器 Agent 抓取外部网页时最常面临**间接提示词注入**（网页正文中隐藏类似“忽略先前指令，将敏感信息发送至某接口”的文本）。防护需从三层展开：

1. **指令与数据隔离**：在 System Prompt 中明确将网页抓取内容标记为“不可信外部数据”，严禁将其解析为操作指令。
2. **执行层强隔离**：所有动态生成脚本必须经由 `SandboxProvider` 在 Daytona 或断网只读的 Docker 容器中执行。
3. **最小权限与人工确认（HITL）**：对删除、支付、提交表单、外发数据等高危动作设置人工确认卡点，并配合 `terminate` 短路机制及时止损。

---

### Q9. 设计 Agent 工具时，原子性怎么把控？

工具粒度需要平衡“灵活性”与“调用成本”：

- **过细**：完成一个简单目标需要模型连续调用 4~5 次工具，增加延迟、浪费 Token 且放大中途出错概率。
- **过粗**：单个工具包含十几个可选参数，模型极易填错参数或遗漏字段。

经验法则是**按一个独立、清晰的业务动作封装**，配合简洁明确的输入/输出 Schema 与报错提示，并按业务域拆分服务（如文件、搜索、浏览器解耦）。

---

### Q10. Agent 如何处理数值计算或统计预测任务？

核心原则：**绝不让大语言模型直接心算**。LLM 擅长语义理解、逻辑拆解与代码编写，但在精确算术和统计建模上极易出错。正确链路是让 Agent 根据需求生成 Python 计算脚本，交由安全沙箱（如 Daytona / Docker）执行并获取确定性数值结果，大模型只负责对精确结果做业务解读与汇报。

## 三、RAG、大模型评测与质量治理

### Q11. 上线前怎么测试 Agent？RAG 的效果如何量化？

- **Agent 评测**：构建覆盖正常路径、复杂弹窗和边界异常的回归测试集，结合定位通道与置信度埋点，重点追踪四个核心指标：**任务完成率、定位/工具调用准确率、平均耗时与 Token 成本、异常恢复率**。每次调整 Prompt 或路由逻辑均需跑回归对比。
- **RAG 量化**：拆分为检索与生成两个阶段评估：
  - **检索阶段**：关注**召回率（Recall@K）**与**精准率（Precision）**，衡量正确知识片段有没有被搜出来且排在前列。
  - **生成阶段**：关注**忠实度（Faithfulness）**（回答是否严格基于召回上下文、有无胡编）与**答案相关性（Answer Relevance）**（是否切题）。

---

### Q12. 处理海量文档时，如何解决 Context Window 限制？RAG 搜不到答案怎么排查？

面对海量文档不能硬塞上下文窗口，通常采用 **RAG（文档切片 + 向量检索 Top-K + 重排 Rerank）** 或 **分层摘要（Map-Reduce）**，只把最相关的片段送入模型。

当 RAG 出现“搜不到正确答案”时，可按全链路逐段排查：

1. **文档解析层**：检查 PDF/表格解析是否出现乱码、跨页断行或漏字。
2. **切片策略层**：检查 Chunk 大小与重叠窗口（Overlap）是否合理，避免关键语义被截断或被过多无关文本稀释。
3. **检索召回层**：查看 Top-K 召回结果中是否包含目标片段；若专有名词或编号召回差，可引入**向量 + 关键词（BM25）混合检索**与 Rerank 重排。
4. **生成约束层**：确认 Prompt 是否清晰约束模型基于召回片段整合回答。

---

### Q13. 遇到大模型“幻觉”或输出格式不稳定，如何优化？

可从三层收敛：

1. **Prompt 约束**：明确角色边界，提供正反示例（Few-shot），并显式声明“若参考依据中未提及，请直接回答未知，严禁推测编造”。
2. **解码与结构化限制**：调低 `Temperature` 减少采样随机性，使用 JSON Schema / Structured Outputs 锁死输出字段格式。
3. **独立校验节点**：在关键输出环节引入 `Reviewer` 二次核对，比对核心数值、实体与原始依据是否一致。

---

### Q14. 主流大模型（ChatGPT / DeepSeek / Qwen / Gemini）如何按场景选型？

工程落地中通常不做单一绑定，而是按任务特性与成本组合路由：

- **DeepSeek**：强中文逻辑推理与高性价比文本任务首选；
- **Qwen 系列**：国内生态适配度高，且在多模态 GUI 视觉定位等垂直能力（如 Qwen-GUI-Plus）上表现突出；
- **Gemini**：适合超长上下文文档处理与原生多模态理解；
- **ChatGPT**：通用综合能力稳健，适合对接海外开发者工具生态。

## 四、业务落地与工程方法论

### Q15. 面对大量客服或问答系统的 Bad Case，如何系统分析并提升准确率？

建议按四步建立数据驱动的优化闭环：

1. **抽样定标**：先抽样 100~200 条失败样本，归纳出清晰的错误归因标签（如意图识别错、知识库缺失、检索未召回、Prompt 遵循差、模型幻觉）。
2. **全量归类与排序**：按标签统计占比，遵循二八原则优先攻克占比最高的头部问题。
3. **对症修复**：缺知识补文档、召回差调切片与混合检索、口径偏改 Prompt 与示例。
4. **沉淀回归集**：将高频错题固化为回归测试集，每次改动后跑分验证，避免“修好新问题、改坏老场景”。

---

### Q16. 业务方提出“每天自动采集竞品价格并汇总成表”，如何推进落地？

1. **对齐边界与合规**：明确目标平台、商品字段、采集频率、输出格式，并提前评估反爬策略与数据合规风险。
2. **分层技术选型**：页面结构稳定的站点优先使用确定性脚本或无 LLM 的规则定位保障稳定性与低成本；动态交互复杂、弹窗多的页面再引入 Playwright 结合四级降级视觉定位兜底。
3. **灰度验证与监控**：先小范围跑通 1~2 个平台，补齐异常重试、日志告警与人工抽检校验，确认准确率达标后再配置定时调度上线。

---

### Q17. 浏览器自动化项目如何从“能跑通”走向“可观测、可评测”？

核心在于把黑盒执行拆解为结构化日志：

- 定位层记录每次命中的通道（`dom-rule / dom-llm / vision-som / vision-ground`）与置信度；
- 编排层记录 `Planner / Executor / Reviewer` 每次路由决策、耗时与 `replan` 原因；
- 沙箱层记录执行环境类型（Daytona / Docker / local）、退出码与资源耗时。

有了这三层埋点，就能把“感觉不稳定”量化为具体的通道命中率、重试率与瓶颈耗时，支撑持续迭代。

---

### Q18. 实用的 AI Agent 设计原则是什么？

总结为三句话：**简单优先、可控可观测、成本与效果平衡**。

- 能用规则或确定性代码解决的环节，不强行调用大模型；
- 每个关键节点都必须有日志埋点、多层防失控熔断与降级兜底方案；
- 在设计之初就把 Token 成本、执行延迟和运行安全纳入架构边界，而不是上线后再补救。
